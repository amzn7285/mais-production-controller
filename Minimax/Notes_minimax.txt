Production Controller – Production Readiness Review
The four production-killer risks (in priority order)
1.
Concurrency — the controller will run many productions at once; nothing in the design caps "many" or protects the system from itself.
2.
Backpressure & resource bounds — without explicit limits on in-flight work, queue depth, and per-run memory, the first traffic spike will take the service down.
3.
Failure isolation — one flaky provider or one malformed Master JSON must not corrupt controller state, leak memory, or block other productions.
4.
Operational visibility — without an explicit state machine, structured logs, and metrics, the team is debugging blind at 2 a.m.
Critical gaps in the current shape
#	Gap	Why it bites in production
M1	Explicit State Machine missing	States are derived from "which agents responded" — race conditions, invalid transitions, untraceable retries.
M2	No idempotency at controller entry	Duplicate submissions = duplicate cost.
M3	No resource governor	First burst exhausts memory and provider quotas.
M4	No bounded queues	Unbounded growth → OOM.
M5	No cancellation API	Stuck runs are unkillable.
M6	No per-agent or per-wave timeout	A hung agent blocks the whole production forever.
M7	No circuit breaker per provider	Flapping providers block the pipeline.
M8	No dead-letter handling	Failures silently disappear.
Architectural smells (look fine, hurt in prod)
"Stateless" but holding ExecutionPlan in memory between agent calls → restart loses work.
Synchronous aggregation at every wave → controller's request thread is blocked for the whole wave.
Implicit state machine (no FSM) → impossible-to-test transitions.
Magic thresholds in code instead of config.
Errors logged as strings → unsearchable, unalertable.
No schema_version on internal messages → silent breakage on schema change.
No graceful shutdown → SIGTERM loses user submissions.

Thread & async safety – the items that bite first
T1 Mutable shared state for pending_productions → use thread-safe map or push to State Manager.
T2 Double-dispatch on duplicate production_id → idempotency under a lock.
T3 Time-of-check / time-of-use on state.status → CAS or per-production_id mutex.
T4 Background tasks orphaned when request thread returns → hand off to a worker; never tie agent lifecycles to request lifecycles.
A1 Blocking call inside the event loop → all IO async.
A2 asyncio.create_task without storing the reference → task GC'd mid-flight, silent data loss.
A3 Cancellation not propagated → agents keep running after user cancels.
A6 CPU-bound step on the event loop (large JSON validation) → run in a thread pool.
Security baseline (all 🟢 Must Have)
Auth (API key minimum, OAuth2 / JWT preferred).
Input size limit (e.g. 256 KB) and depth/complexity limit.
Secrets in env / Vault only — never in request body, never in logs.
Rate limit per caller (token bucket).
TLS everywhere; mTLS internally if you have it.
Provider keys live in the Provider Adapter's secret store, not the controller.
Idempotency keys with TTL = replay protection.
CVE scan in CI on every build.

The one-slide rule for the team
1.
Make the state machine explicit — if you can draw it, you can test it.
2.
Checkpoint every transition, not just the final result.
3.
Bound everything — concurrent, in-flight, memory, wall-clock, log size, queue depth.
4.
Fail fast, fail loud, fail structured. Bad input → 400, never retry.
5.
Be async end-to-end — no blocking calls in the event loop.
6.
Authenticate, authorize, rate-limit, size-limit at the edge.
7.
Observe or die — logs + metrics + traces + audit log. All four.
8.
No secrets in code, config, logs, or request body.
9.
Idempotency is not optional.
10.
Cancel is a feature.
